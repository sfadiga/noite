# M0: Toolchain + Hotkey Latency Spike Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Install the build toolchain, then measure whether Tauri 2 with a hidden, pre-warmed WebView2 window can go from hotkey press to a focused TipTap editor within the D5 budget, without losing keystrokes.

**Architecture:** A throwaway Tauri 2 + React + TipTap app in `spikes/hotkey-latency/`. The Rust side registers the global shortcut and timestamps it. The frontend reports when the editor is focused and painted. A PowerShell harness fires the hotkey and types immediately afterwards. Results go to a findings doc that decides go/no-go. The spike code is kept for reproducibility and never imported by the real app.

**Tech Stack:** Rust stable (MSVC), Node.js LTS + npm, Tauri 2 (latest 2.x), `tauri-plugin-global-shortcut` 2.x, React 18+ + TypeScript, TipTap (`@tiptap/react`, `@tiptap/pm`, `@tiptap/starter-kit`), PowerShell 5.1.

**Spec:** [`docs/spec.md`](../../spec.md) — §2 performance budget (D5), §5 capture window (D6).

## Global Constraints

- Windows 10/11 x64 only (D2).
- Latency budget: hotkey press → editor focused, caret ready **≤ 100 ms**; idle memory **≤ 80 MB** (D5).
- The capture window is created at startup, kept hidden, and only shown/focused on hotkey (D5).
- Hotkey opens an always-on-top window centred on the monitor with the active window (D6).
- Default capture hotkey `Ctrl+Alt+N` (D24).
- Spike code lives only under `spikes/`; nothing outside `spikes/` and `docs/spikes/` imports it.

## Review Focus

1. **Foreground lock:** Windows may refuse `SetForegroundWindow` to a background process. The window then appears but keystrokes still go to the previous app. Task 4 counts lost/misdirected keystrokes with Notepad as the previous foreground app.
2. **WebView2 suspension:** a long-hidden WebView2 can be throttled, making the first show after idle slow. Task 5 measures after 15 min idle and after sleep/resume.
3. **Elevated foreground app** (Task Manager running as admin): UIPI can block focus or input. Task 5 checks manually.
4. **Second monitor / mixed DPI:** the window must centre on the monitor with the active window and stay crisp. Task 5 checks manually.
5. **Hotkey pressed while the capture window is already visible:** must refocus, not toggle or flash. Task 3 handles it; Task 5 checks it.

### Task 3: Instrument hotkey → ready → hidden

**Files:**
- Modify: `spikes/hotkey-latency/src-tauri/src/lib.rs`
- Modify: `spikes/hotkey-latency/src/App.tsx`
- Results written to: `spikes/hotkey-latency/results/trials.csv` (gitignored)

**Interfaces (spike-internal):**
- Rust state: `Mutex<Option<std::time::Instant>>` holding the last press time, plus a trial counter.
- Tauri commands: `report_ready()` and `report_hidden(text: String)`.
- Event: `capture:shown` (Rust → frontend).

- [ ] **Step 1: Register `ctrl+alt+n` in Rust** with `tauri_plugin_global_shortcut::Builder::new().with_shortcuts(["ctrl+alt+n"])` and a `.with_handler`. On `ShortcutState::Pressed` it stores `Instant::now()`, increments the trial, then calls `show()`, `center()` on the `capture` window, `set_focus()`, and emits `capture:shown`. If the window is already visible, do the same (refocus, don't hide).

- [ ] **Step 2: Implement `report_ready`.** It computes `pressed_at.elapsed()` in ms (f64), keeps it per trial, and `report_hidden(text)` appends `trial,ready_ms,text` to `results/trials.csv` (creating it with a header if missing). It then hides the window.

- [ ] **Step 3: Frontend.** Mount one TipTap `useEditor({ extensions: [StarterKit] })` at startup. On `capture:shown`: `editor.commands.focus('end')`, then `requestAnimationFrame(() => requestAnimationFrame(() => invoke('report_ready')))`, so the measurement includes a painted frame. On `Esc`: `invoke('report_hidden', { text: editor.getText() })`, then `editor.commands.clearContent()`.

- [ ] **Step 4: Manual check**

Run: `npm run tauri dev`, press `Ctrl+Alt+N`, type `hi`, press `Esc`. Repeat 3×.
Expected: the window appears focused with a caret, `hi` lands in the editor, and `results/trials.csv` has 3 rows with plausible `ready_ms` and `text` = `hi`.

- [ ] **Step 5: Commit**

```bash
git add spikes/hotkey-latency/src-tauri/src/lib.rs spikes/hotkey-latency/src/App.tsx
git commit -m "spike: instrument hotkey to editor-ready latency"
```

### Task 4: Automated trial harness

**Files:**
- Create: `spikes/hotkey-latency/run-trials.ps1`
- Create: `spikes/hotkey-latency/measure-memory.ps1`

- [ ] **Step 1: Write `run-trials.ps1 -Trials 50`.**
  1. Start Notepad once.
  2. For each trial: activate Notepad (`(New-Object -ComObject WScript.Shell).AppActivate('Notepad')`), wait 300 ms, `SendKeys.SendWait('^%n')`, then **immediately** `SendKeys.SendWait('hello')`, wait 400 ms, `SendKeys.SendWait('{ESC}')`, wait 700 ms.
  3. A trial fails if its `trials.csv` row has `text` ≠ `hello` (characters dropped or misdirected). At the end, the script prints the failed-trial count. Notepad is left open so any leaked characters can be seen.

  Requires `Add-Type -AssemblyName System.Windows.Forms`.

- [ ] **Step 2: Write `measure-memory.ps1`.** Find `hotkey-latency.exe`, recursively collect child processes via `Get-CimInstance Win32_Process` (`ParentProcessId`), which picks up the `msedgewebview2.exe` tree. Print per-process and total `WorkingSet64` and `PrivateMemorySize64` in MB.

- [ ] **Step 3: Dry run**

Run: `npm run tauri build -- --debug` once, start the built exe, then `powershell -File run-trials.ps1 -Trials 5` and `powershell -File measure-memory.ps1`.
Expected: `trials.csv` gains 5 rows with `text` = `hello`, Notepad is empty, and a memory table is printed.

- [ ] **Step 4: Commit**

```bash
git add spikes/hotkey-latency/run-trials.ps1 spikes/hotkey-latency/measure-memory.ps1
git commit -m "spike: add trial harness and memory probe"
```

### Task 5: Run the scenarios and record findings

Use a **release** build (`npm run tauri build`) so the measurements reflect shipping speed.

**Files:**
- Create: `docs/spikes/2026-10-hotkey-latency.md`

- [ ] **Step 1: Warm.** Run 50 trials back-to-back. Record p50, p95, max `ready_ms`, and the number of trials where `text != "hello"` or Notepad received characters.

- [ ] **Step 2: Idle.** Leave the app idle for 15 min, then run 10 trials. Record the first trial separately, plus p95.

- [ ] **Step 3: Sleep/resume.** Sleep the PC, wake it, unlock, then run 10 trials. Record the first trial and p95.

- [ ] **Step 4: Memory.** After 5 min idle, run `measure-memory.ps1`. Record the totals.

- [ ] **Step 5: Manual checks** (pass/fail each):
  - With Task Manager (elevated) in the foreground, the hotkey still opens a focused editor.
  - On a second monitor with the active window there, the capture window centres on that monitor and renders crisply.
  - Pressing the hotkey while the window is visible keeps it focused, with no flicker or hide.

- [ ] **Step 6: Write the findings doc.** Include a table of the measurements above and a verdict against these gates:

| Gate | Pass condition |
|---|---|
| G1 warm latency | p95 `ready_ms` ≤ 100 |
| G2 idle + resume latency | p95 ≤ 100 in both; first-trial values reported |
| G3 keystrokes | 0 lost or misdirected in all trials |
| G4 manual checks | all pass |
| G5 idle memory | total private bytes ≤ 80 MB (report even if it fails) |

- [ ] **Step 7: Commit**

```bash
git add docs/spikes/2026-10-hotkey-latency.md
git commit -m "docs: record hotkey latency spike findings"
```

- [ ] **Step 8: Gate decision (STOP, user decides).**
  - **G1–G4 pass:** Tauri 2 is confirmed. If G5 fails, propose a revised D5 memory target based on the measured WebView2 overhead, and ask the user to accept it or reject it.
  - **Any of G1–G4 fails:** don't continue to M2. Present the numbers and the options (e.g. a native Win32 capture window in Rust with WebView2 only for the board; a lighter capture editor; relaxing D5), and wait for the user's choice.
